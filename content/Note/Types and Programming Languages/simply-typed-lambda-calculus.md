## Introduction

The simply typed lambda calculus is an extension of the [[/Note/Types-and-Programming-Languages/untyped-lambda-calculus.md | untyped lambda calculus]] that incorporates a *type system*. In this system, every term has a type, and the type system enforces rules for how terms can be combined. The goal is to introduce typing rules for variables, abstractions, and applications that maintain type safety (i.e., satisfy the type preservation and progress theorems) and are not too conservative (i.e., they should assign types to most of the practical programs we want to write).

A small caveat is that since pure lambda-calculus is Turing complete, the typechecker might need to solve the halting problem to determine if a term is well-typed.

## Function Types

To give types to functions (i.e., abstractions), we introduce a *type constructor* $->$ for function types. If $T_1$ and $T_2$ are types, then $T_1 -> T_2$ is the type of functions that take an argument of type $T_1$ and return a value of type $T_2$.

> [!info] Definition: Simple Types
> The set of *simple types* over the base type $mono("Bool")$ is generated by the following grammar:
>$$
>#import "@preview/simplebnf:0.1.2": *
>#bnf(
> Prod(
>   $T$,
>   annot: $sans("Type")$,
>   {
>     Or[`Bool`][_boolean_type_]
>     Or[$T_1 -> T_2$][_function_type_]
>   },
> ),
>)
>$$
> The type constructor $->$ is right-associative, so $T_1 -> T_2 -> T_3$ stands for $T_1 -> (T_2 -> T_3)$.

## Typing Relation

In order to assign a type to an abstraction we need to know two things:

- what will happen when the abstraction is applied to some argument;
- what type of arguments to expect.

For the latter, we can either

- simply annotate the $lambda$-abstraction with the intended type of its argument, or
- analyze the body of the abstraction and try to deduce the type of its argument.

In general, languages that used the first approach are called *explicitly typed* languages (also known as the *Church-style*), while those that use the second approach are called *implicitly typed* languages (also known as the *Curry-style*). We will focus on the explicitly typed version of the simply typed lambda calculus, as it is simpler to define and reason about.

Once we know the type of the argument, it is clear that the type of the function's result will be just the type of the body:

$$
#import "@preview/curryst:0.6.0": rule, prooftree

#prooftree(rule(
	name: [**T-ABS**],
	[$tack.r lambda x : T_1. t_2 : T_1 -> T_2$],
	[$x : T_1 tack.r t_2 : T_2$],
))
$$

Since the term can contain free variables, we will need the *typing context* (also called a *type environment*), which is a sequence of variables and their types. We follows the convention that the new bound variable is distinct from all the variables in the context. $Gamma$ can thus be thought of as a finite function from variables to their types. Following this intuition, we write $italic("dom")(Gamma)$ for the set of variables bound by $Gamma$.

The rule for typing abstractions has the general form:

$$
#import "@preview/curryst:0.6.0": rule, prooftree

#prooftree(rule(
	name: [**T-ABS**],
	[$Gamma tack.r lambda x : T_1. t_2 : T_1 -> T_2$],
	[$Gamma, x : T_1 tack.r t_2 : T_2$],
))
$$

The other rules are quite straightforward. The rule for variables states that if a variable $x$ has type $T$ in the context $Gamma$, then $x$ has type $T$:

$$
#import "@preview/curryst:0.6.0": rule, prooftree

#prooftree(rule(
	name: [**T-VAR**],
	[$Gamma tack.r x : T$],
	[$x : T in Gamma$],
))
$$

And the rule for applications states that if $t_1$ is a function that takes an argument of type $T_(11)$ and returns a value of type $T_(12)$, and $t_2$ is an argument of type $T_(11)$, then the application $t_1 t_2$ has type $T_(12)$:

$$
#import "@preview/curryst:0.6.0": rule, prooftree

#prooftree(rule(
	name: [**T-APP**],
	[$Gamma tack.r t_1$ $t_2 : T_"12"$],
	[$Gamma tack.r t_1 : T_"11" -> T_"12"$],
	[$Gamma tack.r t_2 : T_"11"$],
))
$$
